## 一、测试目标与场景选择

### 1.1 目标

1. 摸清核心接口在不同并发下的**响应时间分布**与**吞吐能力上限**；
2. 定位系统的**性能瓶颈**并给出根因；
3. 确认系统在高并发下是否出现**错误率上升**；
4. 输出可复用的压测脚本与可复现的测试方法。

### 1.2 为什么选这三个接口

| 场景 | 接口 | 选它的理由 |
|---|---|---|
| **登录** | `POST /admin/login` | 系统入口，**唯一包含 CPU 密集型运算（BCrypt 密码校验）**的接口，且调用频率高，最可能出现瓶颈 |
| **商品列表查询** | `GET /product/list` | 后台访问量最大的查询接口，走索引 + 分页，代表**数据库读场景** |
| **订单查询** | `GET /order/list?status=1` | 核心业务查询，条件过滤 + 分页，代表**带条件的数据库读场景** |

三个接口构成一组对照实验：**同机、同 JVM、同数据库连接池**，唯一变量是接口自身的业务逻辑 —— 这让后面的瓶颈归因变得非常清晰。

## 二、测试设计

### 2.1 并发梯度

| 参数 | 取值 |
|---|---|
| 并发线程数 | **20 / 50 / 100 / 200** |
| 爬坡时间（Ramp-up） | 10 秒 |
| 稳定运行时长 | 45 秒 |
| 循环次数 | -1（不限，由时间控制） |
| 合计配置数 | 3 场景 × 4 并发 = **12 组** |

### 2.2 脚本设计要点

**① CSV 参数化**：登录接口从 `users.csv` 读取账号，避免固定单账号造成的缓存假象。

```csv
username,password
admin,macro123
macro,macro123
```
> 账号经实测筛选：`ums_admin` 表 8 个账号中仅 `admin`、`macro` 可用默认口令 `macro123`。

**② 接口关联（token 自动传递）**：商品/订单接口需要 JWT 鉴权，采用 setUp 线程组先登录，再通过三级传递把 token 交给主线程组 —— 这与 Postman 的接口关联是同一套思路：

```
setUp 线程组
  └── POST /admin/login
        ├── JSON 提取器        $.data.token  →  变量 ${token}
        └── JSR223 后置处理器   props.put("token", vars.get("token"))   ← 写入全局属性
                                                              ↓
主线程组
  └── HTTP 信息头管理器   Authorization: Bearer ${__P(token)}
```
> **为什么需要 JSR223 这一层**：JMeter 的变量（`vars`）是**线程私有**的，setUp 线程组里取到的 token 主线程组读不到，必须用 `props`（全局属性）跨线程组传递。

**③ 断言**：每个采样器都挂 JSON 断言，断言 `$.code = 200`（业务码），而不是只看 HTTP 状态码 —— 原因见接口测试报告：本项目所有响应 HTTP 都是 200。

**④ 参数化运行**：并发、爬坡、时长通过 `-J` 传入，一份脚本可跑任意梯度：
```bash
jmeter -n -t 登录接口压测.jmx -Jthreads=200 -Jramp=10 -Jloops=-1 -Jduration=45 -l result.jtl
```

### 2.3 ⚠️ 测试方法的一次返工（重要）

> 这一节是本次性能测试最有价值的部分，面试可重点讲。

**第一轮用的是「固定循环次数法」**（`loops=10`），结果算出的 TPS 是 **100、200** 这种非常整齐的值，而且商品列表接口在 200 并发下平均响应时间只有 **4ms**，比 20 并发时的 7ms 还快 —— 这不合常理。

**问题定位**：固定循环次数导致单次运行只有 1~10 秒，而爬坡就占了 2~10 秒，**运行时长几乎完全被 ramp-up 阶段占据**。我算出来的 TPS 实际上是爬坡期的平均值，**由梯度设置决定，而不是服务端能力决定**。这解释了为什么数值如此整齐。

**结论：这种测量方式得到的数据不成立，不能用来下任何结论。**

**第二轮改为「固定持续时间法」**：
- 显式爬坡 10 秒（让线程数爬满）；
- 稳定运行 45 秒；
- **只统计爬坡结束之后的稳态区间**（丢弃前 10 秒），用稳态区间的样本数 ÷ 稳态区间时长 计算 TPS。

改造后数据立刻变得自洽（见第四节的小定律验证）。

> **第一次的数据我保留在 `results/_第一轮-固定循环次数法（方法有缺陷，仅作返工证据保留）/` 目录下**，作为方法返工的记录。**测试方法不严谨，后面的分析全是空中楼阁** —— 这是我在这个项目里最想强调的一条经验。

### 2.4 踩坑记录：JMeter scheduler 不生效导致压测跑飞

改造过程中遇到一个问题：把 `scheduler` 写成参数占位符后：

```xml
<!-- ❌ 错误写法：<boolProp> 不解析函数占位符 -->
<boolProp name="ThreadGroup.scheduler">${__P(scheduler,false)}</boolProp>
```

执行 `-Jscheduler=true` 后，压测**完全不停止**，一直跑下去（实测跑到 4 分 49 秒、4 万多个样本仍在继续），必须手动终止。

**根因**：JMeter 的布尔属性 `<boolProp>` **不会解析 `${__P()}` 这类函数占位符**，`Boolean.parseBoolean("${__P(scheduler,false)}")` 得到 false，scheduler 静默退化为关闭状态；而循环次数设的是 -1（无限），于是变成无限压测。

**正确写法**：布尔值必须硬编码。

```xml
<!-- ✅ 正确写法 -->
<boolProp name="ThreadGroup.scheduler">true</boolProp>
<stringProp name="ThreadGroup.duration">${__P(duration,60)}</stringProp>
```

> 注意：字符串属性（`num_threads`、`ramp_time`、`duration`）**是**能正常解析 `${__P()}` 的 —— 这很容易让人误以为布尔属性也行，从而掉进坑里。**这个坑很隐蔽，因为 JMeter 不报错，只是"参数静默失效"。**

## 四、核心发现

### 发现 1：登录接口存在明确的吞吐上限 —— 约 167 TPS ⭐

把登录接口的 TPS 单列出来看：

| 并发 | 20 | 50 | 100 | 200 |
|---|---|---|---|---|
| **TPS** | 136.1 | 166.6 | 167.2 | **167.6** |

**并发从 50 增加到 200（翻了 4 倍），TPS 纹丝不动地停在 167 左右**，而响应时间从 298ms 一路涨到 1160ms（翻了近 4 倍）。

**这是典型的资源饱和特征**：系统已经到达处理能力上限，此时继续加压**不会提升吞吐，只会让请求排队、响应时间等比例恶化**。这是系统开始「雪崩」的前兆 —— 进一步加压最终会导致超时和错误。

### 发现 2：商品/订单查询的吞吐上限约为登录的 5 倍

| 接口 | 吞吐上限（TPS） | 首档响应时间（20并发 P95） |
|---|---|---|
| 登录 | **~167** | 264 ms |
| 商品列表查询 | **~800** | 58 ms |
| 订单查询 | **~830-900** | 26 ms |

商品和订单查询在 200 并发下 P95 也只有 365ms / 234ms，**比登录接口在 50 并发下的表现还要好**。

### 发现 3：用「小定律」验证数据自洽性 ⭐

**Little's Law（小定律）**：`平均并发数 L = 吞吐量 λ × 平均响应时间 W`

用实测数据反推验证（取 200 并发档）：

| 接口 | 并发 L | 实测 TPS λ | 实测平均响应 W | 理论 W = L/λ | 偏差 |
|---|---|---|---|---|---|
| 登录 | 200 | 167.6 | 1,159.9 ms | 200/167.6 = **1,193 ms** | **2.8%** |
| 商品列表 | 200 | 791.9 | 250.4 ms | 200/791.9 = **252.6 ms** | **0.9%** |
| 订单查询 | 200 | 901.0 | 220.7 ms | 200/901.0 = **222.0 ms** | **0.6%** |

**三个接口的理论值与实测值偏差都在 3% 以内**。这说明了三件事：

1. **测量数据是自洽可信的** —— 不是采样偏差或统计错误；
2. **线程确实处于满载状态** —— 小定律成立的前提就是并发数被完全利用，如果线程有空闲（比如被 ramp-up 摊薄），实测响应时间会显著低于理论值；
3. **稳态窗口的切分是正确的** —— 如果混入了爬坡期的数据，这个等式不可能对得这么准。

> 这一步验证很重要：它把「我觉得数据没问题」变成了「数据在数学上自洽」。面试时讲这一点，能体现你不只是会跑工具，而是**理解指标之间的内在关系**。

### 发现 4：错误率全程为 0%

12 组压测、合计 **约 30 万个请求，错误率全部为 0%**。

**这说明系统的瓶颈表现为「延迟上升」，而不是「请求失败」** —— 在 200 并发下，登录接口的平均响应时间已经超过 1 秒，但没有一个请求报错。

**这是需要警惕的信号**：错误率 0% 容易让人误判「系统很稳」，实际上用户已经等了 1 秒以上。**如果压力继续加大，响应时间会继续线性上升，直到触及客户端超时或 Tomcat 线程池上限，届时错误率会从 0% 突然跳升** —— 这就是典型的「雪崩」模式。所以**不能只看错误率来判断系统健康度**。

## 五、瓶颈分析

### 5.1 为什么登录接口是瓶颈？—— 对比分析法定位到 CPU

**推理链条**：

**第一步：横向对比，缩小范围**

三个接口跑在**同一个 JVM、同一个 Tomcat、同一个 Druid 连接池、同一个 MySQL** 上，唯一变量是接口自身的实现。既然商品/订单能跑到 800+ TPS，而登录只有 167 TPS，**瓶颈必然不在应用容器、网络或数据库基础设施层，而在登录接口自身的业务逻辑**。

**第二步：看实现差异**

| 接口 | 主要工作 |
|---|---|
| 登录 | 查用户 → **BCrypt 密码校验** → 生成 JWT → 写 Redis |
| 商品/订单查询 | 走索引的 SQL 查询 → 分页封装 |

**BCrypt 是故意设计成计算密集型的哈希算法**（通过可调的工作因子抵抗暴力破解，默认 strength=10 意味着 2¹⁰ 轮迭代）。每次登录校验都要消耗可观的 CPU 时间，这是它区别于普通查询的根本原因。

**第三步：用曲线特征验证「CPU 饱和」假设**

不同瓶颈类型的表现特征不同：

| 瓶颈类型 | 并发升高时的表现 |
|---|---|
| **CPU 饱和** | 响应时间**近似线性上升**，吞吐量**很快触顶后持平** ← 登录接口正是如此 |
| 数据库连接池耗尽 | 请求阻塞在获取连接，吞吐触顶，且活跃连接数会持续等于 max-active |
| 外部服务/网络延迟 | 吞吐触顶但响应时间分布会出现明显的多峰（部分请求快速失败） |

登录接口的实测曲线 —— 并发 50→100→200，TPS 恒定 167，响应时间 298→591→1160（几乎精确的线性）—— **完全符合 CPU 饱和的指纹**。

**第四步：旁证**

- 压测期间观察到 `mall-admin` 进程的 **CPU 时间累计达到 2665 秒**（单机压测约 40 分钟），CPU 长期处于高位；
- 商品/订单查询这类轻量场景下，同等并发时 CPU 占用明显更低。

### 5.2 其他已识别的性能风险点

| 风险点 | 现状 | 潜在影响 |
|---|---|---|
| **Druid 连接池上限偏低** | `max-active: 20`，`min-idle: 10` | 并发超过 20 后，请求需排队等连接。这是商品/订单 TPS 在 800 附近触顶的可能原因之一 —— 200 个并发线程争抢 20 个数据库连接 |
| **生产日志级别为 debug + 日志切面记录全量报文** | `logging.level.com.macro.mall: debug`，且 `WebLogAspect` 会把完整请求参数与完整响应体以 INFO 级别打印 | **实测数据：每请求约 6.4 KB 日志，本次 30 万次压测请求产生了 1.84 GB 日志文件**。日志 I/O、字符串拼接与磁盘写入是实打实的开销，高并发下的隐性成本。详见[缺陷报告](defect-report.html)的 DEFECT-05 |
| **单机部署** | 压测机与被测服务同机 | JMeter 自身在 800+ TPS 时也消耗大量 CPU，会与应用争抢资源（见第六节局限性） |
| **无缓存** | 商品列表每次查库 | 商品数据读多写少，适合加 Redis 缓存，可显著降低数据库压力 |

## 六、测试局限性说明（必须说明）

> 诚实说明局限性，是性能报告专业性的体现。

1. **压测机与被测系统同机部署**：JMeter 在商品/订单查询 800+ TPS 的负载下自身也消耗大量 CPU 与内存，会与被测应用、MySQL 争抢资源。因此**商品/订单查询测得的 ~800 TPS 天花板，可能部分来自压测机自身的限制，而非纯粹的服务端能力**。要得到更准确的服务端上限，**应将压测机与被测服务分离部署**。

2. **未做长时间稳定性测试**：本次单档最长 55 秒，属于**短时压力测试**，无法发现内存泄漏、连接池泄漏、GC 随时间的劣化等**长稳问题**。生产评估应补充 1~2 小时的长时间运行测试。

3. **未覆盖更极端的并发**：最高只压到 200 并发。建议继续加到 500/1000 并发，观察错误率何时从 0% 跳升，以确定系统的**崩溃临界点**。

4. **单机单实例**：未测试集群/负载均衡下的表现，无法评估水平扩展的实际收益。

5. **数据规模有限**：`pms_product` 仅 38 行、`oms_order` 仅 65 行，数据量小，查询几乎全部命中缓存和内存。**生产环境的数据量下，数据库查询的响应时间会显著高于本次结果**，性能结论不能直接外推。

## 七、性能调优建议

按「投入产出比」排序：

| 优先级 | 建议 | 预期收益 |
|---|---|---|
| **高** | **登录接口限流 + 验证码前置**：对 `/admin/login` 按 IP/账号做限流（如 Guava RateLimiter 或 Redis 计数），并引入图形/行为验证码，把机器刷登录挡在 BCrypt 之前 | 直接保护最脆弱的 CPU 资源，防止恶意登录打死整个服务 |
| **高** | **生产环境关闭 debug 日志**：改为 `info` 或 `warn`，或仅在排障时按需开启 | 减少日志 I/O 与字符串拼接开销，降低 CPU 占用 |
| **中** | **登录接口水平扩展**：BCrypt 是无状态 CPU 运算，多实例部署可线性提升吞吐（167 TPS × N） | 最直接的吞吐提升手段 |
| **中** | **调大 Druid 连接池**：`max-active` 从 20 提高到 50~100，并配合压测确定最优值 | 缓解连接等待，提升查询类接口吞吐 |
| **中** | **商品列表加缓存**：商品数据读多写少，用 Redis 缓存列表与详情，设置合理过期时间 | 大幅降低数据库压力与响应时间 |
| **低** | **评估 BCrypt strength**：默认 10 可考虑降至 8，在安全性与性能间权衡（需安全团队评估） | 单次校验 CPU 开销约降低 4 倍，但会削弱抗暴力破解能力 |
| **低** | **引入 APM 工具**（SkyWalking / Arthas）定位热点方法 | 把「推断」变成「实测」，精确到方法级耗时 |

## 八、结论

| 结论 | 内容 |
|---|---|
| **系统吞吐能力** | 登录 ~167 TPS；商品列表查询 ~800 TPS；订单查询 ~830-900 TPS |
| **延迟表现** | 200 并发下登录 P95 = 1284ms（偏高，用户体验受影响）；商品/订单 P95 = 365ms / 234ms（可接受） |
| **稳定性** | 12 组共约 30 万请求，**错误率 0%**；但延迟随并发线性上升，属于「未崩溃但在恶化」的状态 |
| **瓶颈定位** | **登录接口的 BCrypt 密码校验是 CPU 密集型运算**，构成系统最明显的性能瓶颈；商品/订单为数据库索引查询，表现良好；Druid 连接池上限 20 是查询类接口的潜在约束 |
| **数据可信度** | 经 Little's Law 交叉验证，理论值与实测值偏差 < 3%，数据自洽可信 |
| **方法学收获** | 压测必须区分爬坡期与稳态期，只统计稳态区间；布尔型配置不能用函数占位符 |

> 原始 12 组 `.jtl`（约 60 MB）与第一轮返工数据保留在本地，未随作品集发布；报告中的所有指标均可在汇总 CSV 与 200 并发 HTML 报告中对上。

### 复现命令

```bash
cd test-artifacts/jmeter

# 稳态压测（推荐）：爬坡10s + 持续45s
jmeter -n -t "登录接口压测.jmx" -Jthreads=200 -Jramp=10 -Jloops=-1 -Jduration=45 -l results/run.jtl

# 生成 HTML 报告
jmeter -g results/run.jtl -o results/html-report
```

> **注意**：必须用 `-n`（非 GUI）模式压测，GUI 模式本身消耗大量资源会导致结果失真。另外 HTML 报告的输出目录必须**事先不存在或为空**，否则 JMeter 会报错。
