> 测试方式：真打包、真部署、真调接口、真压测，所有结论可追溯到原始数据

## 一、测试目标

1. 验证 mall 电商系统在本地环境可完整构建、部署并对外提供服务；
2. 验证登录、商品、订单三大核心模块的功能正确性与异常健壮性；
3. 验证接口的参数校验、鉴权机制、错误处理与响应结构；
4. 摸清核心接口的吞吐能力与延迟分布，定位性能瓶颈；
5. 沉淀可复用的测试资产：用例、脚本、报告、缺陷记录与回归用例。

### 3.1 关键测试策略：断言必须针对业务码

mall 使用统一响应体 `CommonResult`，**所有业务响应（含错误）的 HTTP 状态码都是 200**，真实结果在响应体的 `code` 字段：

```json
{ "code": 200, "message": "操作成功", "data": { ... } }
{ "code": 500, "message": "密码不正确", "data": null }
```

如果只断言 HTTP 200，"密码错误"也会被判为通过。因此全部用例、Postman 断言、JMeter JSON 断言均针对业务码。

1. 本机未安装 Elasticsearch，9200 端口无服务；
2. 横向比对三个模块的 `application-dev.yml`，发现 mall-search 的数据库密码写成 `root`，而实际密码是 `123456` —— 即使装好 ES 也会因连不上数据库而启动失败。

## 五、测试数据策略

- **不重新导入 `mall.sql`**：脚本开头是 `DROP TABLE IF EXISTS`，会清空现有 76 张表、38 个商品、65 笔订单的真实数据。现有数据比空库更有测试价值，因此只做只读校验。
- 从零初始化的正确步骤：先手工 `CREATE DATABASE mall`，再指定库名导入，并加 `--default-character-set=utf8mb4`（脚本来自 MySQL 5.7，不指定字符集中文会乱码）。
- 登录账号：`ums_admin` 存的是 BCrypt 哈希，用项目默认口令 `macro123` 逐个试探 8 个账号，确认仅 `admin`、`macro` 可用。
- 写操作仅保留一条「创建品牌」正向用例，附清理 SQL，测试后还原环境。
- 压测账号通过 `users.csv` 参数化，避免固定单账号造成缓存假象。

## 七、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 中间件缺失（Elasticsearch） | mall-search 无法部署 | 记录依赖矩阵，明确阻塞原因，不强行跳过 |
| 压测机与被测服务同机 | 高并发下 JMeter 自身抢 CPU，吞吐数据可能偏低 | 在报告中明确标注局限性，结论不外推 |
| 数据库字符集为 utf8mb3 | emoji 等 4 字节字符触发 500 | 作为 DEFECT-06 记录，给出整库转 utf8mb4 方案 |
| 测试数据量小（38 商品/65 订单） | 查询性能偏乐观 | 报告中说明数据规模限制，建议生产数据量复测 |
| 写操作用例污染环境 | 数据不可还原 | 仅保留一条写用例，附清理 SQL，优先使用只读用例 |
