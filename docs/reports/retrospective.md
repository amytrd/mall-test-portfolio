> 这份复盘不是"总结成绩"，而是记录**判断过程**：哪些结论是可靠的，哪些方法被推翻过，哪些能力还没有覆盖。

## 一、做对了什么

### 1. 先确认现状，再动手

- 看到 `mall.sql` 开头是 `DROP TABLE IF EXISTS`，没有直接导入，而是先确认库里已有 76 张表和真实业务数据，判断"保留现有数据"比"重建空库"更有测试价值。
- 部署前先做依赖矩阵，发现 mall-search 缺 Elasticsearch，并通过横向 diff 三个模块的 `application-dev.yml`，提前发现数据库密码配置错误（`root` vs `123456`）。

### 2. 不盲从常规套路

- 识别出"所有业务响应 HTTP 都是 200"的项目特性，确立**断言业务码**的策略。如果按常规断 HTTP 200，所有错误用例都会假通过。
- 接口断言不只看 `code`，还校验数据层：按品牌过滤时遍历结果断言 `brandId` 等于查询条件；密码错误时断言响应里**没有** `token` 字段。

### 3. 用证据链定位根因，而不是猜

- emoji 500：客户端现象 → 服务端日志 → 3 字节/4 字节对照实验 → `information_schema` → MySQL 端复现 → 定位 utf8mb3。
- 日志泄露：日志体积 1.84 GB → 查看内容 → 读 `WebLogAspect` 源码 → 确认无脱敏、INFO 级别、全 Controller 覆盖。
- 每个缺陷都有"现象 + 日志 + 代码/数据库证据 + 修复建议"，不是一句"这里好像有问题"。

### 4. 缺陷闭环，而不是一次性报告

- 6 个缺陷全部固化为 `xfail(strict=True)` 回归用例。修复后用例会变成 XPASS 并判失败，强制更新用例、关闭 Bug。

### 5. 主动暴露局限性

- 性能报告明确写出：压测机与服务同机、未做长稳、数据量小、单实例，结论不能直接外推。
- 自动化报告明确写出：这是 API 集成测试，不是 UI 自动化；未使用 Selenium/Playwright。

## 二、走过的弯路

### 弯路一：压测方法错误，数据全部推翻重做 ⭐

**第一轮**用"固定循环次数"（10 次），单次运行只有 1–10 秒，而爬坡就占了 2–10 秒。算出的 TPS 是 **100、200** 这种整齐整数，商品查询在 200 并发下平均响应时间只有 4ms，比 20 并发时还快 —— 不合常理。

**定位**：运行时长几乎完全被 ramp-up 占据，算出来的是爬坡期平均值，由梯度设置决定，不是服务端能力。

**第二轮**改为"固定持续时间"：爬坡 10s + 稳态 45s，只统计爬坡结束后的稳态区间。数据立刻自洽，并用 Little's Law 验证偏差 < 3%。

**教训**：**测试方法有问题，后面的分析全是空中楼阁。** 看到"过于整齐"的数据要先怀疑测量方法，而不是急着下结论。

### 弯路二：fixture 污染让测试"说谎"

`api` fixture 复用 `raw_api` 对象并设置 token，导致 `raw_api` 也带上了 token。所有"无 token 应被拦截"的负向用例实际带着 token 发出，本该 FAIL 却 PASS。差点误报"商品接口漏配鉴权"。

**修正**：两个 fixture 各自持有独立 `Session`。

**教训**：测试代码也是代码，共享可变状态会产生更危险的 bug —— 它不报错，只让测试悄悄失去防护能力。

### 弯路三：JMeter scheduler 静默失效

把 `scheduler` 写成 `${__P(scheduler,false)}`，`<boolProp>` 不解析函数占位符，`Boolean.parseBoolean` 得到 false，scheduler 静默关闭；循环次数又是 -1，压测无限运行（实测跑到 4 分 49 秒仍在继续）。

**修正**：布尔属性必须硬编码 `true`；字符串属性（线程数、爬坡、时长）才可以解析占位符。

**教训**：工具"不报错"不等于"配置生效"。参数化后要验证实际行为（看运行时长、样本数），不能只看脚本表面。

### 弯路四：PowerShell 与 Maven 的参数解析

`mvn package -Ddocker.skip=true` 在 PowerShell 5.1 中被在点号处拆成两个参数，Maven 报 `Unknown lifecycle phase ".skip=true"`。报的是"生命周期阶段非法"而不是"插件失败"，说明参数压根没被正确识别，应怀疑调用层而不是构建脚本。加引号解决。

**教训**：看错误信息的**层级**判断问题出在哪一层。构建脚本没执行到插件，就不该先怀疑插件。

## 三、关键认知

| 认知 | 说明 |
|---|---|
| 测试方法优先于工具 | JMeter/Postman 只是执行器，方法错了数据就错了；先验证测量方法，再分析结果 |
| 断言要断"数据对不对" | 只断 `code=200` 无法发现"过滤条件没生效""返回了全量数据" |
| 错误率 0% ≠ 系统健康 | 200 并发下登录 P95 已 1.28s，错误率仍是 0%；继续加压会从 0% 突然跳升（雪崩） |
| 平均值会骗人 | 平均值被大量快请求拉平，掩盖长尾；要看 P95/P99 |
| 日志是排障的桥 | 客户端现象与服务端根因之间的唯一通道；尤其当异常被框架掩盖时 |
| 缺陷之间有放大效应 | DEFECT-01（错误掩盖）让 DEFECT-02/06 在客户端完全看不出真相，修复优先级要联动考虑 |
| 测试的终点是"可回归" | 缺陷不提完就结束，要固化为 xfail，修复后自动提醒 |

## 四、能力边界

诚实列出目前**没有覆盖**的部分：

| 维度 | 现状 | 影响 |
|---|---|---|
| UI 自动化 | 未使用 Selenium / Playwright | 无法覆盖前端交互、兼容性、视觉回归 |
| 移动端 | 未使用 Appium | 未覆盖 App 场景 |
| 抓包 | 未使用 Charles / Fiddler | 复杂链路排障少了抓包手段 |
| 性能工具 | 只用了 JMeter | 未使用 Locust / k6 / Gatling |
| 长稳测试 | 单档最长 55 秒 | 无法发现内存泄漏、连接池泄漏、GC 劣化 |
| 数据库断言 | 以接口响应为主 | 未在用例后置 SQL 断言落库结果 |
| 安全测试 | 做了注入/鉴权/信息泄露，非专业渗透 | 不能替代安全专项测试 |
| 集群/负载均衡 | 单机单实例 | 未验证水平扩展收益 |

## 五、下一步计划

1. **补 UI 自动化**：用 Playwright（而非 Selenium）做登录、商品列表的冒烟测试，接入现有 pytest 体系；
2. **补数据库断言**：在 pytest 用例后置 SQL 校验写操作是否真正落库；
3. **CI 真实回归**：搭建可被 GitHub Runner 访问的测试环境，把手动触发改为每日定时；
4. **性能深化**：压测机分离部署、补充 500/1000 并发与 1 小时长稳，接入 Prometheus + Grafana 采集服务端指标；
5. **接口契约测试**：基于 OpenAPI 文档自动校验响应 schema，减少手写字段断言；
6. **安全专项**：系统学习 OWASP Top 10，补充越权、SSRF、反序列化等场景。
